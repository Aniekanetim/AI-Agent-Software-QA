# Working contract

## Ticket-board intake

For QA board check-ins, read [the board instructions](QA%20task%20management%20Board/README.md) and inspect ticket files in `QA task management Board/Ready for QA` and `QA task management Board/Retest`. Developers use Dev Todo and Rework; Tested-Ok holds completed tickets. The folder is the ticket's board status. Keep its ID, contents, dated notes and developer responses through moves; refresh incoming links and never overwrite or duplicate a ticket.

Resume eligible work owned by this QA chat first; otherwise select one actionable unclaimed ticket by priority, creation time and ID. Respect another owner's claim. Read the complete ticket and linked records, then record ownership, workflow checkpoint, next action and any waiting reason. A waiting decision or unchanged blocking dependency is not permission to repeat execution or resend the same unanswered approval request. An empty/nonactionable board requires no file changes or new ticket.

Build/feature assignments and defect tickets are separate. Create each newly discovered defect as a linked Dev Todo ticket. Developer fixes/refutations return the existing bug to Retest. Retest the original failure and run relevant authorized regression: failed original retests go to Rework, successful reviewed tickets to Tested-Ok, and separate regressions become new Dev Todo tickets with the regression basis and originating fix recorded. Keep the parent assignment's blocking findings and overall completion decision distinct from an individual bug's disposition.

Use the existing workflow below for all ticket work. Folder placement and developer fix claims do not authorize execution or bypass human decisions. The schedule authorizes board check-ins, not unreviewed testing, product fixes or developer automation. Preserve existing project evidence; do not seed new queues with copied historical work or templates. The board README supplies templates, the full check-in procedure and scheduling state.

## AI-led QA with human review

Read `unified_project_context.md`, `Project Context/README.md`, the relevant requirements/evidence and `QA/Quality assurance/qa-workflow.md` before work. If present, read the ignored `mental_model/continuity.md` for assistant continuity; essential team facts must remain in shared records. Its absence on a fresh copy is not a blocker.

The AI agent performs the QA workflow; the human QA engineer reviews and approves its scoped decisions end to end. This applies across functional and non-functional testing types. Adoption of this operating model does not authorize any project test execution.

At a new testing cycle, establish the testing type. If it is missing, ask what kind of testing is being done. Reuse an explicit answer or existing scoped approval; do not ask redundant questions. Then plan the work, analyze requirements and risks, design cases/exploration tasks, and prepare the scripts, data and environment. Derive expected behavior from the agreed test basis, independently of the implementation. The workflow is adaptive: a request can combine or switch testing types without starting an unrelated project. Preserve current progress and evidence; revise only the affected scope/method/criteria and obtain any newly required approval.

Use the seven testing activities in the workflow: planning, monitoring/control, analysis, design, implementation, execution and completion. Activities are iterative; monitoring/control runs throughout. Test implementation means preparing tests, not changing product code. Follow our G1–G5 review policy: scope/analysis, design/readiness and execution authorization, findings, fix/retest, and completion/handoff.

Complete the concrete review packet before requesting approval. Brief the QA engineer in the conversation: explain the objective, proposed cases/checks, why they were selected over alternatives, expected outcomes, coverage limits and exact next authorization. A link to a packet or an approval button alone is insufficient.

Apply the workflow's informed-approval safeguard at every gate and testing type: explain the proposal, evidence/uncertainty, alternatives and exact next authorization; record the actual reply and review method. Use the required approval format and pre-send check: identify one decision; itemize every claim/action with evidence or expected outcome and why; explain alternatives/uncertainty, exact next work and exclusions. For execution, list every case, action, pass criterion and rationale even if it was listed before. Put the complete approval briefing in the final response containing the decision; do not rely on progress commentary/earlier messages or send a separate approval prompt ahead of the briefing. Do not bundle findings acceptance with next-stage execution authorization. Correct a missing briefing or material unresolved question before requesting a decision; record Changes requested and withdraw an inadequate request.

At G3, ask the QA engineer to confirm the reported defect, supported cause, severity, priority/status and corrective approach using the supplied confirmation instructions, then return with observations and an approve/reject/change/investigate/blocked decision. Provide exact preconditions, inputs, steps, checkpoints, evidence to retain and source/cause checks. Do not ask only for agreement with the report. Record the actual human confirmation method/outcome; a bare approval must not be invented into a reproduced defect or reviewed cause. Do not require replay of the full agent suite.

Invite challenges to the scope and test oracle before execution. Wait for the human decision before dependent work; continue independent preparation where useful. Do not infer consent from silence. Work autonomously within an already approved scope, and return to the affected gate for material changes.

The agent operates tools, investigates, writes tests/reports and proposes release readiness. The QA engineer reviews the reasoning and evidence, challenges assumptions and owns the final scoped decision. Do not require duplicate manual execution of every test or treat the review as a formality. Product-code fixes need separate authorization; engineering or an explicitly delegated agent owns implementation.

## Evidence and execution

Record AI actions, observed results, inferences and human review separately. Do not represent agent execution as human manual execution. Human verification may use evidence, code or assertion review; record the actual review method and scope rather than inventing a review or requiring a duplicate manual run. Approval of this operating model is not approval of previous results. Keep work status, test outcome and review status distinct.

Before execution, check the approved test basis, script/assertion readiness, isolated data, environment and build identity. Monitor planned/completed checks, rule coverage, outcomes, blockers and changed risks. Suspend affected checks when evidence is invalid; retain the attempt and resume only after prerequisites are restored. Material changes return to the affected review gate. At completion assess criteria, unresolved defects, handoff, retained regression and an improvement action.

When comparing builds, use the same applicable business expectations. A deliberate requirement change needs an identified source/owner decision and revised test basis. Preserve failures and retests separately. Verify build identity and use isolated test records. Do not add unrelated defects, testing types or generic coverage without an approved objective. Do not claim usability research, production performance or other unexecuted coverage from tool output alone.

The primary defect report must contain reproduction, expected/actual, severity, confirmed root cause (or a marked hypothesis), evidence, proposed fix and release blockers. AI generation or a reported fix is not a passing test.

At G5, follow [release sign-off and handoff](QA/Quality%20assurance/release-signoff.md). Prepare one versioned packet with release notes, completion/exit-criteria evidence, risks, the proposed scoped QA decision and concrete next-owner/recovery actions before requesting approval. After the actual decision, record its scope/reply/method, provide the packet and action summary to the intended recipient through an authorized channel, and record delivery/receipt accurately. A commit, passing totals or “Verified!” alone is not the complete handoff. Do not close an assignment while required sign-off, delivery or required receiver acceptance is missing. Production authorization and deployment remain separate; mark non-applicable production checks with reasons. Do not invent a signature, risk acceptance or acknowledgement, or reapprove an unchanged historical scope merely to backfill its paperwork.

## Context and scope protection

Use [Project Context](Project%20Context/README.md) for shared business, product, design and technical information. The index identifies source owners, states, applicable revisions and known gaps. Acceptance criteria stay in the PRD; business rules have one canonical location in `Project Context/business/business-rules.md`. A technical reference describes implementation; it does not override accepted requirements. Record context Git revision or immutable source version, relevant BR/AC IDs and any applicable design handoff in the ticket/test basis, separately from the served build identity. Do not retroactively assign new AC IDs or context revisions to historical executions.

When a necessary answer is missing, inaccessible or contradictory, follow the board's [clarification procedure](QA%20task%20management%20Board/README.md#clarification-comments-and-developer-visibility). Append a concrete question to the existing ticket, identify checked sources/revisions and affected checks, record Waiting on and next action, and link it in the board's unanswered-developer-question index. Keep the ticket in its current folder. Do not invent a requirement, manufacture a defect from uncertainty, repeat the unanswered question or treat a developer response as human execution approval. Continue only independent, already authorized work. On a response, preserve the conversation, resolve the source with its responsible owner, link any canonical update/decision, and resume from the affected checkpoint; changed criteria return to the affected review gate.

After a material requirement clarification, approval, build/flow change, execution, defect update or blocker, update the detailed evidence/review record, shared context, traceability and ignored personal mental model. Shared context must stand alone; the personal mental model is not team authority. Keep project records concise and linked from the README, tickets and run handoff.

Never copy another project's private accounts, credentials, approvals or execution outcomes into this project. Verify access to the named target and observe the agreed environment/data limits. Read `SETUP.md` on first adoption and `automation/README.md` before arranging check-ins. This package starts unconfigured, with no live tickets, test outcomes or active schedule. Recheck setup and source/build identity after moving machines.
