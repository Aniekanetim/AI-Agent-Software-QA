# Working contract

## Onboard before assigned work

Before tool setup questions, follow [shared tool discovery](automation/tools/README.md). Inspect the actual calling harness, existing executable selections and native integrations. Reuse compatible working setup and supplied choices. Distinguish installation, harness access, command compatibility, authentication, resource permissions and actual operation evidence. Do not reinstall for a harness restriction or restart onboarding after switching hosts; reverify only affected capabilities and retain prior records. A version probe is not a completed browser/API operation.

Use [Postman CLI](automation/postman/README.md) for applicable collection-based tasks. Local files need no Postman login. Cloud work needs selected identity/resources and explicit reporting scope. Match verification to the current account, region and credential source; after a change, check affected capabilities before assuming login is needed. Login guidance with `required: null` means unresolved verification, not permission or a request to sign in. Authenticate only when required. Keep Postman credentials separate from target-API credentials. Never use postman init as discovery, create accounts automatically, or assume MCP/desktop sign-in proves CLI access.

For new adoption, read [guided onboarding](Onboarding/onboarding-workflow.md), inspect existing preparation and show its roadmap. Prepare project/context/access/tools/operating preferences rather than asking the user to select a testing category. Use one focused missing question at a time across onboarding, authentication, mail selection and settings; retain clear extra answers, actual prompt/response references and interrupted-save recovery. Do not pretend helper JSON was displayed to a human. Respect pause/resume, Back, Cancel and Close settings.

Establish all five context domains through provide/discover/combined routes. Discovery remains independent. Human-source transcription into named baseline documents needs explicit maintenance authorization; observations remain in the AI store. Never treat an empty template or inferred behavior as an approved requirement.

Offer in-app browser, Playwright CLI, Playwright MCP or an evidence-based recommendation; library/Test stay available for scripted suites. Record actual method/visibility/context and capability evidence. Separate a local MCP server rehearsal from connection to the current host. Recheck sessions/access; tool installation and saved choices are not operational readiness.

Discover provider/account metadata through actual host integrations, including its integration directory if Gmail is not exposed initially. Present Gmail/Workspace prominently and let the user select the actual account/mailbox; reuse a valid selection. AgentMail, other providers, human assistance and later setup remain choices. Do not open message bodies merely to identify accounts. Bind scope/environment, verify required content access, correlate OTP/link attempts and retain redacted evidence without secrets. Outbound mail/cleanup needs its own authorization.

Apply the [global test-mailbox policy](automation/email/mailbox-policy.md); do not require users to invent a policy. After confirming provider/application plus support and the actual permissions, configure the selected physical binding's standard recipient policy. Use `email account` to prepare and record distinct identity/purpose/run aliases for fresh account state; use reuse mode and the exact original alias for continuation/retests. Record creator/profile, objective and starting state; preparation is not application registration or observed starting state. Match verification to the exact tagged recipient, purpose/sender and trigger time, never an arbitrary latest email. Keep physical inbox and application alias identities separate. Refresh inbox metadata on requested rechecks or reported changes, and retain old snapshots as history. Account creation and email access still follow the actual project scope.

Select actual GitHub repositories and verify identity/access. Polling or event intake identifies assignments; it does not authorize execution. A reusable regression policy requires the full informed briefing and actual approval for its exact command/suite/target/reporting scope. Match fresh PR identity to actual tested build, deduplicate unchanged revisions and preserve uncertainty. Retain G3 findings and G5 sign-off decisions. A preference is not an active connection/schedule/trigger. Keep the master unconfigured; see [automation](automation/README.md).

## Choose the pipeline and preserve context ownership

Requests identify what to do; execution procedures identify how. Use [Product Discovery](Product%20Discovery/README.md) and its [workflow](Product%20Discovery/discovery-workflow.md) for learning objectives. Use the existing five-folder board and QA workflow for testing/defects. Do not force discovery requests through QA statuses or apply QA test/release gates as discovery completion states. An explicit QA ticket can link a discovery request; read both records and retain their separate authorization/checkpoints.

Read relevant sources in both context stores. Root `Project Context/` is maintained by the human team and responsible owners; accepted applicable sources establish product expectations. `Product Discovery/Project Context/` is maintained by the agent and holds evidence-backed observations, inferences and gaps. During discovery or QA execution, do not edit files under the root `Project Context/`; propose a clarification on the originating request/ticket and let the human owner maintain the baseline. An explicit human assignment to edit a specified baseline document is a separate maintenance task, not implied authority from discovery or testing. Neither location alone establishes approval or freshness.

The agent can update its discovery knowledge, tickets, evidence and shared progress within authorization. Keep observations, interpretations, review of capture accuracy and actual owner decisions distinct. Main-context revisions, discovery entry versions and served application identity are separate references. Missing intended behavior can permit observation but blocks dependent correctness judgments. No automatic copying or promotion occurs between stores.

For hosted discovery, no application checkout is required. Follow the discovery access/session procedure, use only authorized roles/actions and keep credentials/session state out of committed records. Preserve sources and progress across interruption; do not repeat unchanged exploration, unanswered questions or approval requests. This package enables no discovery scheduler.

## Ticket-board intake

For QA board check-ins, read [the board instructions](QA%20task%20management%20Board/README.md) and inspect ticket files in `QA task management Board/Ready for QA` and `QA task management Board/Retest`. Developers use Dev Todo and Rework; Tested-Ok holds completed tickets. The folder is the ticket's board status. Keep its ID, contents, dated notes and developer responses through moves; refresh incoming links and never overwrite or duplicate a ticket.

Resume eligible work owned by this QA chat first; otherwise select one actionable unclaimed ticket by priority, creation time and ID. Respect another owner's claim. Read the complete ticket and linked records, then record ownership, workflow checkpoint, next action and any waiting reason. A waiting decision or unchanged blocking dependency is not permission to repeat execution or resend the same unanswered approval request. An empty/nonactionable board requires no file changes or new ticket.

Build/feature assignments and defect tickets are separate. Create each newly discovered defect as a linked Dev Todo ticket. Developer fixes/refutations return the existing bug to Retest. Retest the original failure and run relevant authorized regression: failed original retests go to Rework, successful reviewed tickets to Tested-Ok, and separate regressions become new Dev Todo tickets with the regression basis and originating fix recorded. Keep the parent assignment's blocking findings and overall completion decision distinct from an individual bug's disposition.

Use the existing workflow below for all ticket work. Folder placement and developer fix claims do not authorize execution or bypass human decisions. The schedule authorizes board check-ins, not unreviewed testing, product fixes or developer automation. Preserve existing project evidence; do not seed new queues with copied historical work or templates. The board README supplies templates, the full check-in procedure and scheduling state.

## AI-led QA with human review

Read `unified_project_context.md`, `Project Context/README.md`, `Product Discovery/Project Context/README.md`, `QA Process Context/README.md`, the relevant requirements/discoveries/evidence and `QA/Quality assurance/qa-workflow.md` before QA work. Discovery follows its own procedure above. If present, read the ignored `mental_model/continuity.md` for assistant continuity; essential team facts must remain in shared records. Its absence on a fresh copy is not a blocker.

The AI agent performs the QA workflow; the human QA engineer reviews and approves its scoped decisions end to end. This applies across functional and non-functional testing types. Adoption of this operating model does not authorize any project test execution.

At a new testing cycle, read the task and applicable context, changes and risks, then determine the testing activities and coverage. Ask only for material missing intent, access, limits or decisions; do not routinely ask the human to classify testing. Plan, analyze, design and prepare scripts, data and environment. Derive expected behavior from the agreed test basis independently of the implementation. Activities can combine or change as the task requires. Preserve progress/evidence, revise only affected scope/method/criteria and obtain any newly required approval.

Use the seven testing activities in the workflow: planning, monitoring/control, analysis, design, implementation, execution and completion. Activities are iterative; monitoring/control runs throughout. Test implementation means preparing tests, not changing product code. Follow our G1–G5 review policy: scope/analysis, design/readiness and execution authorization, findings, fix/retest, and completion/handoff.

Complete the concrete review packet before requesting approval. Brief the QA engineer in the conversation: explain the objective, proposed cases/checks, why they were selected over alternatives, expected outcomes, coverage limits and exact next authorization. A link to a packet or an approval button alone is insufficient.

Apply the workflow's informed-approval safeguard at every gate and testing type: explain the proposal, evidence/uncertainty, alternatives and exact next authorization; record the actual reply and review method. Use the required approval format and pre-send check: identify one decision; itemize every claim/action with evidence or expected outcome and why; explain alternatives/uncertainty, exact next work and exclusions. For execution, list every case, action, pass criterion and rationale even if it was listed before. Put the complete approval briefing in the final response containing the decision; do not rely on progress commentary/earlier messages or send a separate approval prompt ahead of the briefing. Do not bundle findings acceptance with next-stage execution authorization. Correct a missing briefing or material unresolved question before requesting a decision; record Changes requested and withdraw an inadequate request.

At G3, ask the QA engineer to confirm the reported defect, supported cause, severity, priority/status and corrective approach using the supplied confirmation instructions, then return with observations and an approve/reject/change/investigate/blocked decision. Provide exact preconditions, inputs, steps, checkpoints, evidence to retain and source/cause checks. Do not ask only for agreement with the report. Record the actual human confirmation method/outcome; a bare approval must not be invented into a reproduced defect or reviewed cause. Do not require replay of the full agent suite.

Invite challenges to the scope and test oracle before execution. Wait for the human decision before dependent work; continue independent preparation where useful. Do not infer consent from silence. Work autonomously within an already approved scope, and return to the affected gate for material changes.

The agent operates tools, investigates, writes tests/reports and proposes release readiness. The QA engineer reviews the reasoning and evidence, challenges assumptions and owns the final scoped decision. Do not require duplicate manual execution of every test or treat the review as a formality. Product-code fixes need separate authorization; engineering or an explicitly delegated agent owns implementation.

## Evidence and execution

Record AI actions, observed results, inferences and human review separately. Do not represent agent execution as human manual execution. Human verification may use evidence, code or assertion review; record the actual review method and scope rather than inventing a review or requiring a duplicate manual run. Approval of this operating model is not approval of previous results. Keep work status, test outcome and review status distinct.

Before execution, check the approved test basis, script/assertion readiness, isolated data, environment and build identity. Monitor planned/completed checks, rule coverage, outcomes, blockers and changed risks. Suspend affected checks when evidence is invalid; retain the attempt and resume only after prerequisites are restored. Material changes return to the affected review gate. At completion assess criteria, unresolved defects, handoff, retained regression and an improvement action.

When comparing builds, use the same applicable business expectations. A deliberate requirement change needs an identified source/owner decision and revised test basis. Preserve failures and retests separately. Verify build identity and use isolated test records. Do not add unrelated defects, testing types or generic coverage without an approved objective. Do not claim usability research, production performance or other unexecuted coverage from tool output alone.

The primary defect report must contain reproduction, expected/actual, severity, confirmed root cause (or a marked hypothesis), evidence, proposed fix and release blockers. AI generation or a reported fix is not a passing test.

At G5, follow [release sign-off and handoff](QA/Quality%20assurance/release-signoff.md). Prepare one versioned packet with release notes, completion/exit-criteria evidence, risks, the proposed scoped QA decision and concrete next-owner/recovery actions before requesting approval. After the actual decision, record its scope/reply/method, provide the packet and action summary to the intended recipient through an authorized channel, and record delivery/receipt accurately. A commit, passing totals or “Verified!” alone is not the complete handoff. Do not close an assignment while required sign-off, delivery or required receiver acceptance is missing. Production authorization and deployment remain separate; mark non-applicable production checks with reasons. Do not invent a signature, risk acceptance or acknowledgement, or reapprove an unchanged historical scope merely to backfill its paperwork.

## Context and scope protection

Use the [human context index](Project%20Context/README.md) to locate owners, source states, applicable revisions and known gaps. Acceptance criteria stay with human product requirements; business rules have a canonical human source in `Project Context/business/business-rules.md` or its linked authority. The [discovery context](Product%20Discovery/Project%20Context/README.md) supplies practical learning without overriding those sources. Record each context's applicable revision/entry versions, BR/AC and OBS IDs, and any design handoff separately from the served build identity. Do not retroactively assign new IDs or revisions to historical executions.

When a necessary answer is missing, inaccessible or contradictory, follow the board's [clarification procedure](QA%20task%20management%20Board/README.md#clarification-comments-and-developer-visibility). Append a concrete question to the existing ticket, identify checked sources/revisions and affected checks, record Waiting on and next action, and link it in the board's unanswered-developer-question index. Keep the ticket in its current folder. Do not invent a requirement, manufacture a defect from uncertainty, repeat the unanswered question or treat a developer response as human execution approval. Continue only independent, already authorized work. On a response, preserve the conversation, resolve the source with its responsible owner, link any canonical update/decision, and resume from the affected checkpoint; changed criteria return to the affected review gate.

After a material clarification, approval, build/flow change, execution, defect update or blocker, update the detailed evidence/review record, agent-managed discoveries where affected, shared progress and traceability; update an ignored personal note only if used. Propose any necessary human-baseline change to its owner instead of editing root Project Context. Shared records must stand alone; the personal mental model is not team authority. Keep records concise and linked from requests, tickets and handoffs.

Never copy another project's private accounts, credentials, approvals or execution outcomes into this project. Verify access to the named target and observe the agreed environment/data limits. Read `SETUP.md` on first adoption and `automation/README.md` before arranging check-ins. This package starts unconfigured, with no live tickets, test outcomes or active schedule. Recheck setup and source/build identity after moving machines.

## Maintain QA process context

Before preparing or resuming testing, read [QA Process Context](QA%20Process%20Context/README.md) and the applicable strategy, design/exploration, coverage, configuration, data and regression records. These are agent-maintained operational records under reviewed policy, not another product-requirement authority. Name actual accountable owners and preserve source/review/revision references. Reuse canonical records; do not duplicate results or rewrite human requirements.

Distinguish target/interface, quality objective, scenario perspectives, techniques and execution method. Consider meaningful positive, negative and edge cases; labels overlap and never multiply case counts. Use focused charters for creative/exploratory investigation. Explain selections and material exclusions, not a fixed technique/case quota. Keep QA charters distinct from independent discovery requests.

At G1/G2 link the applicable process basis, risk/condition IDs, cases/charters, data and configuration. Record designed versus exercised coverage and actual outcomes by scope/run/build. Unknown intent blocks dependent Pass/Fail judgments; retain authorized observations with their limits. Update affected traceability and retained regression after execution/clarifications. At G5 expose untested items, residual gaps and next-owner maintenance actions through the existing packet and ticket.

On changes, assess affected records and mark Needs review; preserve historical results and prior approvals. Routine operational updates remain within existing authorization, while material scope/criteria/action changes return to the affected gate. Do not rerun every test or restart onboarding solely because a record changed. Use the optional read-only coverage helper only as a structural/count check; inspect canonical records and never treat its output as execution, proof of accepted intent or product sign-off.
